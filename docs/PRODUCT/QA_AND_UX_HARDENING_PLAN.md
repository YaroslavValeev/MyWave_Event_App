## 1. Решение владельца (зафиксировано)

- Сборки **Android и iOS будут**. Это этап **после** отладки текущей формы, не вместо неё.
- Сейчас продукт = **веб-приложение (PWA)** + API. Это та же бизнес-логика, которая потом войдёт в оболочки Android/iOS.
- Нативные APK/IPA **не собирать и не имитировать**, пока не закрыт полевой контур на PWA.
- Отладка идёт на том, что уже есть: браузер телефона + десктоп + staging.

Почему так: баги ролей, судейства, чек-листа и публикации дешевле ловить в PWA. Оболочка магазина их не лечит.

---

## 2. Цель ближайшего цикла

Сделать так, чтобы **организатор, участник и судья** провели одно событие на телефоне без обучения интерфейсу и без Excel как SoT.

Критерий готовности к сборкам Android/iOS:

1. Staging крутит **этот** 0.5.10, не образ 0.5.9.
2. Три роли прошли сценарий на реальном экране телефона (не только pytest).
3. P0-баги и P0-дыры безопасности закрыты.
4. Карточка события понятна без 10 равных вкладок (хотя бы Control Room + Athlete home + Judge current).
5. Сайт честно ведёт на Event App; нативные кнопки не врут.

## 4. Последовательность (не параллелить конфликтующее)

### Волна 0 — вывести 0.5.10 на staging (1–2 дня, владелец + агент)

Зависимость: ветка `cursor/p0-import-center-athlete-link`, коммит `6ce503b`.

1. Backup SQLite staging по [BACKUP_RESTORE.md](../OPERATIONS/BACKUP_RESTORE.md).
2. Деплой **только** Event App compose staging, не боты и не Flask-сайт.
3. Smoke:
   - `GET /health` → `db_ok: true`, app не врёт версию
   - `GET /api/v1/app-downloads/manifest` → documentation `available`, android/ios/source `unavailable`
   - Web `/projects/checklist-org#mywave-event-app` открывается
   - Гость по-прежнему не видит `draft` события
4. Rollback: предыдущий compose-образ + backup БД.

**Стоп-фактор:** пока staging на 0.5.9, письмо сайту указывает это явно. Не обещать сайту, что 0.5.10 уже в бою.

### Волна 1 — отладка текущих сценариев (P0, 3–5 дней)

Прогон на телефоне 360 px и на десктопе. Каждый шаг: баг → фикс → повтор.

DoD волны 1: таблица багов с severity; P0 закрыты; pytest зелёный. Сценарий **1.10** не блокирует 1.4–1.7: сначала состав/оценки, затем насыщение эфира.

**Cursor:** чинить найденное, не начинать Control Room, пока 1.4–1.7 не стабильны.  
**Владелец:** пройти 1.1–1.9 руками на staging.

Rollback: git revert фикс-коммита; БД не откатывать без нужды.

### Волна 2 — безопасность и устойчивость (параллельно с хвостом волны 1)

Не пентест «для галочки», а закрытие известных поверхностей.

| ID | Работа | Почему сейчас | Owner |
|----|--------|---------------|-------|
| S1 | SMTP на staging | OTP в mail_outbox ломает полевой вход | владелец |
| S2 | Проверка authz регрессии: participant 403 на lock/publish | UI не должен быть единственной защитой | агент |
| S3 | Uploads: MIME, размер, path containment — регресс-тест | документы/протоколы/**field-media** | агент |
| S4 | Analytics ingest: нет PII в props | уже allowlist, не расширять ключами email/phone | агент |
| S5 | Handoff download: не светить URL в HTML, rate limit | уже есть; не ломать при правках UI | агент |
| S6 | JWT в localStorage — зафиксировать риск TD-02 | до native и до cookie-сессии | ADR, не молча |
| S7 | LEGAL тексты — рабочие | не блокер отладки; блокер публичного prod | владелец+юрист позже |
| S8 | `npm audit` / pip известных CVE в lockfile | T9 supply chain | агент, без слепого `audit fix` — **TD-19 зафиксирован 2026-09-16** |

Вне скоупа до native: полный pen-test, CSP production, платежи.

### Волна 3 — UX / эргономика (канон Role Based + Live First)

Не новый продукт. Те же данные, другие рабочие места.

Порядок PR (из UX_UI_CANON, не сдвигать):

1. **Athlete Event Home** — «что со мной сейчас»: категория, заезд, номер, очередь, CTA стартового списка.
2. **Organizer Control Room** — Сейчас / Следующий / Требует внимания. Не 10 вкладок первым экраном.
3. **Live Heat polish** — уже начат; добить состояния и ошибки.
4. **Judge Mode** — текущий спортсмен крупно, без выбора «не того».
5. Results + Notifications — русские статусы, deep-link, понятный publish gate.
6. a11y pass после dry-run: клавиатура, 44×44, focus, contrast, русские SR labels.

Анти-паттерны: гигантский PR «весь redesign»; английский UI; анимация вместо feedback; отдельные приложения на роль.

DoD UX-задачи: как в UX_UI_CANON §32.

### Волна 4 — полевой dry-run (владелец, без native)

Состав: организатор + судья + chief_judge на одном событии (Казань как черновик **или** отдельное test event).

Не публиковать результаты Казани автоматически. Карточку события на витрину — только явным решением владельца (`draft` → `published`/`live`), результаты остаются draft.

Сценарий: check-in → heat on water → лист судьи → verify → chief publish одного тестового результата → откат/void если нужно.

Только после этого — разговор о Capacitor/PWA wrapper / Play / TestFlight.

### Волна 5 — подготовка native (ещё не сборка)

Когда волны 0–4 зелёные:

1. Зафиксировать WebView/PWA shell (не второй backend).
2. Список отличий: push, file picker, install prompt, Safe Area, back button Android.
3. Подписать Android (keystore вне git).
4. Apple Developer + TestFlight группа.
5. Прописать URL в env карточки выдачи — тогда кнопки Android/iOS сами станут «доступны».

- Карточка события всё ещё cabinet всех ролей.

- Казань: часть баллов нет; draft; не homologated.
- SMTP нет.
- pytest 104, но нет e2e/axe в CI (TD-04, TD-17).

Не трогать в этом цикле: Telegram/MAX как ядро, volunteer/boat/полный broadcast, ParserNews, EXIF/Athlete-альбом, offline-first. FieldMoment (камера PWA) — срез 1, не заменяет native камеру и не публикует файлы гостю.
