**Статус:** целевой UX / техзадание. **Не является реализацией в staging.**  
**Дата:** 2026-11-04  
**Источники:** скриншоты владельца (3 экрана), просмотр исходного кода `YaroslavValeev/MyWave_Event_App` (ветка `main`), документы `docs/STATUS/CURRENT_STATE.md`, `docs/API/API_CONTRACT.md`, `docs/ARCHITECTURE/DATA_MODEL.md`, IWWF Wakesurf 2026, IWWF EMS 2026.

## Цель

Превратить перегруженный набор вкладок события в **пошаговый центр управления спортивным мероприятием**. Принцип: *статус → действие → необходимые поля → подтверждение → следующая задача*. Гость/участник/судья/организатор видит только разрешённые маршруты. Сервер остаётся единственным источником прав и официальных результатов.

## Подтверждённые элементы существующего кода

- `apps/web/src/app/events/[id]/page.tsx` — единый экран события (~88 КБ), 13 вкладок, `checklist`, `participants`, `training`, `protocol`, `report`, `scoring`, `heats`, `results`.
- `apps/web/src/components/JourneyGuidancePanel.tsx` — подсказки и следующий шаг, но не полная сквозная маршрутизация.
- `apps/web/src/components/LiveScoreboardPanel.tsx` — SSE/polling.
- `apps/web/src/components/EventReportPanel.tsx` — assemble/edit/publish/Excel.
- `apps/web/src/lib/scoreDrafts.ts` — локальная очередь JudgeScore через `localStorage`, без полноценного IndexedDB.
- API уже поддерживает документы, категории на чтение, список участников, чеклист, heats/start-list, judge-scores, protocol-captures, версионные official-protocol, PDF/DOCX, EventReport.
- `CURRENT_STATE.md` указывает v0.5.19, отсутствие Android APK и неисполненный физический dry-run.

**Техническое наблюдение:** в просматриваемом фрагменте блока `docs` кнопка удаления документа не имеет обработчика `onClick`; проверить целиком и либо привязать существующий API метод, либо убрать неработающее действие. Часть полей в `page.tsx` стилизована inline с `background: rgba(0,0,0,0.25)` — отсюда серые поля на светлом фоне.

## Рабочая структура экранов

- **Главная:** приветствие → выбрать цель → выбрать мероприятие.
- **Обзор события:** текущий этап, главная задача, ответственный, прогресс.
- **Подготовка:** документы → категории → судьи → регистрация/медпроверка → посев → тренировки → контроль готовности.
- **День соревнований:** диспетчер заездов, мобильный пульт судьи, таблица результатов.
- **Итоги:** проверки → протоколы и ревизии → отчёты → грамоты → архив.
- Мобильное меню: `Обзор · Подготовка · Заезды · Судья · Итоги`; вложенные операции открываются из действий, без горизонтальной ленты 13 вкладок.

## Правила IWWF и честность автоматизации

### Seeding / heats

- Wakesurf IWWF 2026, Rule 5: первый круг формируется по IWWF Wakesurf Ranking; спортсмены без рейтинга помещаются после рейтинговых, случайным порядком; максимум **6 райдеров** в хите; переходы LCQ/четвертьфинал/полуфинал/финал исходят из **мест**, не сырых баллов. Структуру по количеству участников берут из **Appendix B**, а не из универсального `snake`-алгоритма.
- В IWWF EMS есть обновления для рейтинга Wakeboard Boat за 2026 год: автоматическая система должна хранить дату/версию рейтинга и provenance, не принимать произвольные цифры как «IWWF».
- Правила IWWF/Wakesurf, IWWF/Wakeboard Boat и WWA различаются. `governing_body + discipline + season + rules_version + category + event_level` — обязательные параметры выбранного rule-pack. Нельзя смешивать разные федерации/формулы.
- Алгоритм **только предлагает** посев с объяснением, его утверждает ответственное лицо. Переходы в опубликованный стартовый список создают аудируемую ревизию.

### Judges assignment

- Для wakesurf IWWF 2026 в Rule 13 указан главный судья, назначающий **трёх судей в катер**.
- Проверять квалификацию и срок допуска, назначение на конкретный хит, заявленный конфликт интересов (родство, свой подопечный/клуб, коммерческая зависимость), загруженность, отдых, значение/статус соревнования, необходимые позиции панели.
- Конфликт интересов: требуется подтверждение или отвод с обоснованием. При недостатке допустимых судей **BLOCKED**, а не невалидное автоназначение.
- Решение об утверждении/переопределении — за главным судьёй и полномочными лицами по регламенту. Фиксировать `actor`, `timestamp`, `why`, `rulepack_version`.

### Scoring + speech

- Wakeboard Boat: в действующем примере `IWWF_BOAT_EIC` используются `Execution / Intensity / Composition`. Нельзя применять критерии wakesurf к wakeboard.
- Wakesurf IWWF 2026: `Execution / Intensity / Difficulty / Variety` (1–10 каждое, шаг до 0.1; до 40 на судью); также важна **позиция, определённая судьёй**. Правило приоритета места проверять по правилам, не только суммировать числа.
- Голосовой путь: `разрешение микрофона → запись/диктовка → STT → текст → распознавание терминов → ручное подтверждение → заметка`. Автозаполнение числовых баллов возможно лишь как предложение после отдельной валидации и явного утверждения судьи. Не подменять субъективную оценку автомоделью.
- Для аудиозаписей: минимальный срок хранения, локальный/серверный режим, уведомление пользователя и политика приватности. Транскрипция не должна отправляться стороннему провайдеру без согласованного режима обработки.

### Protocols / reports / certificates

- Uploaded ProtocolCapture = **материал для проверки**, а не утверждённый официальный протокол.
- Approved OfficialProtocolRevision = неизменяемый снимок результатов и реквизитов; любое исправление создаёт новую версию.
- Generated EventReport — отдельный производный документ; исходная таблица результатов не дублируется как новый source of truth.
- Грамоты: только `published` и прошедшие процедуру утверждения результаты. Обязательные поля: athlete ID, ФИО с учётом consent, мероприятие, категория, место, дата, подпись/печать, версия протокола. Не хранить SVG/HTML как доверенный шаблон без sanitization; начните с PNG/JPG или утверждённого PDF.

## API-контракты: сначала искать существующий аналог

**Уже существует (см. текущий API):** `GET /events/{id}/documents`, `GET /events/{id}/participants`, `GET /events/{id}/categories`, `GET /events/{id}/checklist`, `GET/POST /events/{id}/heats`, `GET/POST /events/{id}/heats/{heat_id}/start-list`, `POST /events/{id}/judge-scores`, `POST /events/{id}/judge-scores/aggregate`, `POST /events/{id}/protocol-captures`, `GET /events/{id}/official-protocol`, EventReport и revisions.

**Проектные расширения, не выдавать за существующие:**

```http
PATCH /api/v1/events/{id}/categories/{category_id}
GET   /api/v1/events/{id}/officials/assignments
POST  /api/v1/events/{id}/officials/assignment-proposals
POST  /api/v1/events/{id}/officials/assignments/approve
POST  /api/v1/events/{id}/seeding/preview
POST  /api/v1/events/{id}/seeding/approve
POST  /api/v1/events/{id}/training-slots/preview
PATCH /api/v1/events/{id}/medical-checks/{participant_id}
GET   /api/v1/events/{id}/report-templates
POST  /api/v1/events/{id}/certificates/preview
POST  /api/v1/events/{id}/certificates/batch
```

Контракты требуют согласования существующей модели данных и маршрутов до написания новых endpoints. Не использовать `GET` с побочными эффектами; все mutating endpoints — auth, RBAC, audit, concurrency.
