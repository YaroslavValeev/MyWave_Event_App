# MyWave Event App — сквозной сценарий организатора соревнования

**Статус:** целевая спецификация для реализации и проверки  
**Дата:** 13.09.2026  
**Роль:** организатор соревнования / event manager  
**Продукт:** MyWave Event App; «Champ App» — рабочее название  

## 1. Назначение документа

Это сценарий работы организатора от первого создания события до официального архива. Он предназначен для product, UX, backend, frontend, database, QA, security, DevOps и AI-agent команды.

В документе разделены:

- **Факты** — подтверждено ранее изученными материалами проекта и соревнований.
- **Целевой процесс** — как должен работать организатор в полноценном Event App.
- **Критерии приемки** — что необходимо проверить перед реальным событием.

GitHub-репозиторий `YaroslavValeev/MyWave_Event_App` в текущем подключенном доступе возвращает 404. Поэтому документ не утверждает наличие описанных экранов в текущем коде. После восстановления доступа команда должна сопоставить каждый пункт с существующими моделями и не создавать дублирующие модули.

## 2. Что подтверждено о продукте

MyWave Event App — самостоятельная платформа соревнований. Согласованная Stage 1-архитектура включает web/PWA, FastAPI API `/api/v1`, БД приложения как Source of Truth, а также auth/OTP, роли, events, applications, roster, officials, documents, training slots, consent, notifications и audit log.

В текущей оценке проекта уже есть существенный слой подготовки события, регистрации, ролей, документов и уведомлений, но полноценные heats, start lists, check-in, scoring/results, официальный архив и production/staging остаются главным функциональным разрывом. Целевой тест продукта — провести хотя бы одно соревнование без Excel как основного источника истины.

## 3. Результат работы организатора

Организатор должен получить один управляемый контур:

`создать событие → настроить регламент → загрузить документы → открыть регистрацию → проверить заявки → собрать roster → назначить officials → построить расписание → сформировать heats/start lists → провести check-in → управлять статусами воды → принять оценки → проверить и опубликовать результаты → выдать медиа → собрать feedback → закрыть и архивировать событие`.

В любой момент организатор видит:

- что уже завершено;
- что заблокировано;
- сколько участников ожидают действия;
- какие дедлайны близки;
- кто ответственный;
- какое изменение было сделано и кем;
- что увидит участник;
- можно ли безопасно откатить или исправить действие.

Основная UX-модель — не набор разрозненных таблиц, а рабочая доска события с прогрессом, предупреждениями и ближайшими действиями.

## 4. Роли внутри организационного контура

| Роль | Зона ответственности | Критические действия |
|---|---|---|
| Владелец события | Утверждает регламент, бюджет, публикацию и финальный архив | Публикация события, назначение ответственных, утверждение официального протокола |
| Event manager | Ежедневно ведет событие, участников, расписание и коммуникации | Открытие регистрации, review заявок, roster, сообщения, check-in |
| Регистратор | Обрабатывает заявки и документы | Проверка полей, документов, оплат и статусов допуска |
| Координатор площадки | Ведет прибытие, очередь, группы и оперативные изменения | Check-in, ready, вызов, on-water, задержки |
| Chief judge | Утверждает судейскую схему, правила и финальные оценки | Статус judging, проверка и подтверждение результатов |
| Scorer | Вводит оценки по heat/run | Черновик score, отправка на проверку, исправление до lock |
| Homologator / technical official | Проверяет соответствие условиям и техническим требованиям | Подтверждение пригодности результатов, если предусмотрено регламентом |
| Media manager | Организует фото/видео и сопоставление с Athlete ID | Прием файлов, проверка прав, подтверждение привязки |
| Коммуникационный менеджер | Готовит сообщения участникам, зрителям и партнерам | Публикация анонсов, изменений и post-event коммуникации |
| Support | Решает проблемы доступа, оплаты, документов и аккаунтов | Тикеты, эскалация, без изменения спортивных результатов |
| AI triage agent | Сводит задачи, находит ошибки, предлагает действия | Только рекомендации и черновики; критические действия подтверждает человек |

### Принцип разделения полномочий

Один пользователь не должен незаметно совмещать роли, которые позволяют единолично изменить и ввести, и утвердить официальный результат. Для чувствительных операций нужна схема maker-checker:

`ввод → проверка → утверждение → публикация`.

Каждое изменение роли, допуска, документа, расписания, оценки, протокола, платежного статуса или архива попадает в business audit log с автором, временем, причиной и предыдущей версией.

## 5. Состояния события

Рекомендуемая state machine:

`draft → configured → registration_open → registration_closed → review → roster_locked → schedule_published → live → results_pending → results_verified → published → completed → archived`.

Дополнительные состояния:

- `paused` — временная приостановка регистрации или расписания;
- `postponed` — перенос даты;
- `cancelled` — отмена;
- `correction_pending` — обнаружена ошибка после публикации;
- `archived` — read-only режим.

Переход между состояниями проверяет обязательные условия. Например, нельзя открыть регистрацию без опубликованных категорий, дат, платежей, правил и политики документов; нельзя перевести событие в `live` без roster, officials, расписания и emergency plan; нельзя архивировать событие с незакрытыми критическими инцидентами без явного решения владельца.

## 6. Временная шкала организатора

Фактические даты задаются в событии. Ниже — операционный шаблон относительно первого дня соревнований.

### D‑90…D‑60: решение о проведении

Организатор создает черновик события и заполняет паспорт:

- название;
- тип (клубное, региональное, всероссийское, чемпионат, первенство);
- федерация и статус санкционирования;
- дисциплины;
- даты и часовой пояс;
- место, водоем, адрес, координаты;
- контакт оргкомитета;
- ожидаемая вместимость;
- категории;
- формат раундов;
- требования к судьям и officials;
- платежи;
- бюджетные и партнерские блоки;
- политика фото/видео;
- emergency contacts;
- статус публичности.

**Экран:** «Паспорт события» с процентом заполнения и блокирующими ошибками.

**Необходимо предусмотреть:** копирование структуры предыдущего события, но без автоматического переноса устаревших дат, цен, документов, участников и consent.

### D‑60…D‑45: регламент, категории и документы

Организатор загружает или создает версии документов:

- положение/бюллетень;
- расписание и программа;
- правила дисциплины;
- требования к медицинской справке;
- требования к страховому полису;
- правила допуска и check-in;
- safety briefing;
- media policy;
- политика обработки данных и consent;
- регламент апелляций;
- контакты экстренных служб;
- партнерские материалы — отдельно от официальных документов.

Для каждого файла задаются:

- тип;
- язык;
- версия;
- дата вступления в силу;
- кто видит;
- нужно ли подтверждение прочтения;
- дедлайн;
- замещает ли новая версия предыдущую.

Организатор создает категории и проверяет:

- название категории для интерфейса;
- код категории для API/протокола;
- возрастные границы;
- половые ограничения, если применимо;
- дисциплину;
- минимальное/максимальное число участников;
- формат квалификации, LCQ, полуфинала и финала;
- критерии прохода;
- правила tie-break;
- порядок стартов;
- необходимость лицензии/разряда/медицинского допуска.

**Критерий приемки:** категория в приложении совпадает с формулировкой в официальном бюллетене; код категории не меняется после начала регистрации без миграции и уведомления.

### D‑45…D‑30: настройка регистрации и платежей

Организатор задает:

- дату открытия и закрытия регистрации;
- лимит мест по категории;
- waitlist;
- стоимость федеративного взноса, если он нужен;
- стартовый взнос;
- дополнительные опции;
- способы оплаты;
- возвраты и сроки;
- промокоды или льготы, если разрешены;
- обязательность каждого платежа;
- кто видит финансовые данные.

Участник должен видеть только понятные суммы и назначения. Организатор видит dashboard:

- заявка создана;
- платеж ожидается;
- платеж подтвержден;
- платеж failed;
- ручная сверка;
- возврат;
- неоплаченные заявки по дедлайну.

Нельзя закрывать регистрацию автоматически только по истечению времени без уведомления и audit log. Нельзя хранить полные данные банковских карт в Event App.

### D‑30: публикация анонса и приглашений

Перед публикацией система выполняет preflight:

- указаны даты, место и часовой пояс;
- есть хотя бы одна опубликованная категория;
- определены документы и дедлайны;
- настроены платежи или явно указано «без оплаты»;
- назначен контакт поддержки;
- заданы правила публикации имени, результатов и медиа;
- есть ссылка на правила;
- настроен канал уведомлений.

После preflight организатор публикует событие. Система создает deep link и предлагает сегменты получателей:

- все пользователи;
- прошлые участники конкретных федеративных событий;
- участники выбранной дисциплины;
- регион/клуб;
- вручную выбранные Athlete ID.

Массовая рассылка требует предварительного просмотра и human approval. В audit log сохраняются аудитория, текст, время и автор.

### D‑30…D‑14: прием и проверка заявок

Рабочая очередь организатора должна иметь фильтры:

- новая;
- черновик;
- отправлена;
- не оплачена;
- документы отсутствуют;
- документы на проверке;
- документы отклонены;
- требуется уточнение;
- готова к допуску;
- принята;
- лист ожидания;
- отклонена;
- отозвана.

Карточка заявки содержит:

- Applicant ID и Athlete ID;
- имя и публичное имя;
- телефон — только для уполномоченной роли;
- дату рождения и проверку категории;
- клуб, регион, федеративные данные;
- выбранную дисциплину и категорию;
- платежи;
- документы и статусы;
- согласия;
- историю изменений;
- предыдущие заявки, если доступ разрешен;
- сообщения участнику;
- назначенного проверяющего.

Проверяющий не должен видеть медицинские сведения шире, чем необходимо для решения допуска. Любой отказ содержит причину, поле/документ и дедлайн исправления.

### D‑21: закрытие регистрации и формирование roster

Организатор запускает процедуру:

1. закрывает новые заявки или переводит их в очередь;
2. фиксирует snapshot заявок;
3. проверяет лимиты категорий;
4. выявляет дубли профилей и телефонов;
5. проверяет конфликты категорий и расписания;
6. подтверждает оплату и документы;
7. назначает статус `accepted`, `waitlisted` или `rejected`;
8. назначает Athlete ID и стартовые номера;
9. публикует персональные уведомления.

Roster — версия данных, на основе которой строятся стартовые листы. После `roster_locked` изменение участника создает новую версию и требует повторной проверки затронутых heats.

**Импорт из Excel:** допускается только как migration/import tool. Импорт выполняется в preview:

- найдено строк;
- нормализовано имен;
- найдено дублей;
- конфликтов дат рождения;
- повторов телефонов;
- отсутствующих документов;
- неполных платежей.

До commit организатор видит diff и подтверждает импорт. Excel не становится Source of Truth после загрузки.

### D‑21…D‑14: назначение судей и команды

Организатор создает roster officials:

- chief judge;
- judges;
- scorer;
- homologator;
- announcer/commentator;
- boat driver;
- safety/rescue;
- medical;
- check-in staff;
- media team;
- support;
- technical operator.

Для каждого задаются:

- роль;
- доступ к конкретному событию;
- категории/раунды;
- смена и часовой пояс;
- контакт;
- подтверждение назначения;
- конфликт интересов, если требуется;
- резервная замена.

Система не должна показывать судье лишние персональные документы участника. Комментатор получает спортивный профиль, но доступ к медицинским и финансовым данным запрещен.

### D‑14…D‑7: создание расписания

Организатор задает блоки:

- регистрация;
- мандатная проверка;
- тренировки;
- briefing;
- квалификации;
- LCQ;
- полуфиналы;
- финалы;
- награждение;
- media windows;
- технические паузы;
- резерв погоды.

Для каждого блока:

- начало и плановая длительность;
- буфер;
- площадка/вода;
- ответственная роль;
- видимость для участника;
- условия переноса;
- шаблон уведомления.

Изменение расписания после публикации создает новую версию. Нельзя тихо перезаписывать время в базе: участник должен увидеть, что изменилось, почему и когда.

### D‑10…D‑3: построение heats и start lists

Система должна поддерживать:

- раунд;
- категорию;
- heat;
- порядок участников;
- seed или ручной порядок;
- участника и Athlete ID;
- стартовый номер;
- статус участника;
- плановое время;
- фактическое время выхода;
- переход в следующий раунд;
- резервного участника, если предусмотрено;
- примечание для оператора.

Организатор выбирает способ формирования:

- импорт из утвержденного протокола;
- автоматическая жеребьевка по заданным правилам;
- ручная перестановка с указанием причины;
- перенос участника между heats.

Перед публикацией система проверяет:

- нет ли участника в двух heats одного раунда;
- все ли допущенные участники включены;
- не попал ли недопущенный участник;
- совпадает ли категория;
- достаточен ли интервал между выходами;
- не превышен ли лимит heat;
- сохранен ли порядок и версия.

После publish участник видит только свою релевантную часть, а организатор — полную таблицу.

### D‑2…D‑1: pre-event readiness

Организатор запускает контрольный список:

- опубликованы правила и последняя версия бюллетеня;
- roster locked;
- payments reconciled;
- документы reviewed;
- officials confirmed;
- стартовые листы approved;
- check-in devices tested;
- QR/Athlete ID работает;
- offline cache проверен;
- интернет и резервная сеть проверены;
- scoring devices заряжены;
- резервные контакты доступны;
- погодный/водный план определен;
- emergency и medical route проверены;
- media upload bucket готов;
- уведомления протестированы;
- печатный fallback protocol подготовлен.

В интерфейсе должны быть отдельные состояния `готово`, `требует внимания`, `заблокировано`, `не применимо`.

## 7. День соревнований: операционный сценарий

### 7.1. Открытие площадки

Организатор переводит событие в `live`, фиксируя:

- время открытия;
- ответственного оператора;
- фактическое состояние воды/площадки;
- актуальную версию расписания;
- активную смену officials.

Система показывает live dashboard:

- текущий блок;
- текущий и следующий heat;
- задержка относительно плана;
- количество checked-in;
- количество ready;
- DNS/DNF/withdrawn;
- незакрытые инциденты;
- последний sync time;
- состояние медиа-потока.

### 7.2. Check-in

Оператор сканирует QR участника или ищет по Athlete ID/имени. До подтверждения система показывает предупреждения:

- неоплачено;
- нет одобренной справки;
- просрочен полис;
- нет consent;
- участник не в roster;
- конфликт категории;
- уже checked-in.

Если допуск нельзя решить на месте, оператор создает case и назначает ответственному, не изменяя статус самовольно.

После check-in участник получает push с подтверждением и дальнейшим шагом. Повторное сканирование не создает дубль.

### 7.3. Управление очередью и выходом на воду

Статусы heat:

`scheduled → called → ready → on_water → scoring → completed → locked`.

Статусы participant run:

`not_checked_in → checked_in → ready → on_water → completed / DNS / DNF / DSQ`.

Оператор может:

- вызвать следующий heat;
- объявить задержку;
- отметить фактическое время выхода;
- заменить участника только по предусмотренной процедуре;
- зафиксировать DNS/DNF и причину;
- отправить обновление участникам затронутых heats.

Фактическое время выхода важно для медиа-сопоставления и статистики; оно не должно подменяться плановым.

### 7.4. Ввод и проверка судейских оценок

Scorer вводит оценки в контексте конкретного run:

- event ID;
- round ID;
- heat ID;
- Athlete ID;
- judge ID;
- критерий;
- значение;
- комментарий, если нужен;
- время ввода;
- версия формы.

Расчетный результат строится отдельно от исходных оценок. Пока chief judge не подтвердил раунд, участник видит только «результат формируется».

Минимальная цепочка:

`score draft → scorer submitted → chief judge review → calculation locked → official result published`.

Исправление до lock сохраняет предыдущую версию. Исправление после публикации — это correction workflow с причиной, правами, новой версией и уведомлением.

### 7.5. Переходы между раундами

После lock система применяет правила прохода:

- количество Q;
- tie-break;
- ручное решение chief judge, если допускается регламентом;
- DNS/DNF/DSQ;
- резерв;
- перенос времени.

Организатор подтверждает сформированный следующий раунд до его публикации. Нельзя автоматически отправить участника в полуфинал, если расчет еще не verified.

## 8. Оперативные изменения и инциденты

Организатору нужен единственный журнал operational incidents:

- погода;
- состояние воды;
- неисправность оборудования;
- задержка катера;
- медицинская ситуация;
- конфликт расписания;
- ошибка в стартовом листе;
- технический сбой сети/устройства;
- жалоба участника;
- ошибка медиа;
- спор по результату.

Каждый инцидент имеет:

- тип и приоритет;
- время;
- место;
- ответственного;
- затронутые event/heat/participants;
- текущий статус;
- действия;
- решение;
- вложения;
- audit trail.

### Изменение расписания

1. Организатор выбирает причину.
2. Система показывает затронутые heats и участников.
3. Предлагается новая версия времени.
4. Ответственный подтверждает.
5. Публикуется уведомление с diff.
6. Система отслеживает delivery/open.

### Ошибка в стартовом листе

Публикация блокируется, если ошибка обнаружена до старта. Если старт уже состоялся, создается correction record; старая версия остается доступной в audit, а участники получают объяснение.

### Спор по результату

Участник подает апелляцию через отдельную форму. Организатор видит дедлайн, evidence, ответственного и решение. Статус официального результата не меняется до решения уполномоченного лица.

## 9. Коммуникации организатора

### Каналы

- in-app inbox;
- push;
- email, если подключен;
- Telegram/MAX как дополнительные интерфейсы, не Source of Truth;
- официальный канал события;
- закрытый OPS-чат для команды.

### Шаблоны сообщений

Организатор должен иметь шаблоны:

- приглашение;
- заявка принята;
- нужны исправления;
- платеж не найден;
- документ отклонен;
- roster опубликован;
- стартовый лист опубликован;

- группа началась;
- спортсмен следующий;
- выход на воду;
- heat завершен;
- результат опубликован;
- задержка;
- отмена/перенос;
- апелляция принята;
- медиа готово;
- feedback;
- архив закрыт.

Для каждого сообщения отображаются получатели, preview, переменные, время отправки, delivery status и возможность отменить массовую рассылку до отправки.

## 10. Медиа-контур организатора

Организатор настраивает:

- media team;
- папки события;
- правила именования;
- максимальный размер и MIME;
- storage policy;
- права на оригинал и превью;
- срок действия share links;
- consent для публичной выдачи;
- связь с event/round/heat/Athlete ID.

Рабочий процесс:

`upload → virus/MIME/size check → metadata extraction → suggested match → operator review → published to athlete → archive`.

EXIF/timecode и фактическое время выхода могут использоваться для предложения совпадения, но спорное сопоставление подтверждает оператор. Медицинские и регистрационные документы никогда не попадают в медиа-альбом.

## 11. Завершение соревнования

После последнего финала организатор выполняет post-event checklist:

- все heats закрыты;
- у каждого участника есть финальный спортивный статус;
- все score locks выполнены;
- chief judge подтвердил результаты;
- официальный протокол сформирован;
- protocol PDF/JSON имеет версию и checksum;
- результаты опубликованы;
- медиа-очередь обработана или помечена pending;
- апелляции закрыты или переданы владельцу;
- incident log закрыт;
- feedback отправлен;
- финансовые статусы сверены;
- участникам отправлено post-event сообщение.

Организатор нажимает «Завершить событие». Система показывает блокирующие пункты и список исключений. После подтверждения событие переходит в `completed`, затем — в `archived` после завершения обязательных процедур.

## 12. Архив и исправления после публикации

Read-only архив содержит:

- паспорт события;
- версии бюллетеней и правил;
- roster;
- categories;
- officials;
- heats/start lists;
- результаты по раундам;
- официальный протокол;
- Athlete ID links;
- опубликованные фото/видео;
- notifications;
- апелляции и решения;
- feedback aggregate;
- audit log;
- import manifests.

Нельзя редактировать архив «на месте». Для исправления создаются:

1. причина;
2. автор и проверяющий;
3. ссылка на исходную версию;
4. новая версия;
5. список затронутых участников;
6. уведомление;
7. запись в audit log.

## 13. Дашборд организатора

Главный экран события должен отвечать на пять вопросов:

1. Что происходит сейчас?
2. Что заблокировано?
3. Кому нужно действие?
4. Что изменилось?
5. Какой следующий риск?

Рекомендуемые блоки:

- состояние события;
- countdown до следующего блока;
- заявки: всего / на проверке / приняты / waitlist;
- документы и платежи с ошибками;
- roster completion;
- officials readiness;
- расписание и отклонение от плана;
- текущий heat;
- check-in rate;
- score/results queue;
- media queue;
- incidents;
- unread support cases;
- последний sync и состояние offline.

## 14. Права доступа

Минимальные правила:

- event manager видит и изменяет операционные данные своего события;
- registrar видит заявки и документы, но не меняет scoring;
- scorer вводит оценки, но не публикует официальный результат;
- chief judge проверяет и утверждает scoring;
- media manager видит только необходимые спортивные идентификаторы и consent;
- commentator видит публичный спортивный профиль и разрешенные результаты;
- support не видит медицинские документы без необходимости;
- участник видит только свои документы, заявки, медиа и результаты;
- архив доступен по правилам публичности;
- владелец события может делегировать роль, но каждое делегирование журналируется.

Нужны негативные тесты: попытка открыть чужой документ, изменить чужой результат, опубликовать без chief judge, загрузить файл вне допустимого события, отправить массовое сообщение без approval.

## 15. Аналитика организатора

Без PII собирать:

- время от создания события до публикации;
- долю заявок, завершенных без поддержки;
- среднее время проверки документа;
- долю платежей с ошибкой;
- roster lock success rate;
- долю подтвержденных officials;
- отклонение фактического расписания от планового;
- check-in rate;
- долю DNS/DNF;
- время ввода и публикации результата;
- число corrections/appeals;
- media match rate;
- media delivery/open rate;
- feedback response rate;
- offline conflicts;
- количество и длительность инцидентов.

События аналитики не должны содержать ФИО, телефоны, медицинские данные, номера документов или платежные реквизиты.

## 16. AI Agents и subagents в контуре организатора

AI используется как помощник, а не как судья или владелец соревнования.

| Agent | Разрешенная работа | Обязательное ограничение |
|---|---|---|
| Event Setup Agent | Проверяет заполнение паспорта, категории, дедлайны и документы | Только checklist и предложения |
| Registration Triage Agent | Классифицирует неполные заявки, ищет дубли и конфликты | Не принимает/отклоняет участника окончательно |
| Document Agent | Проверяет формат, срок, наличие полей, готовит подсказку | Не выносит медицинское решение |
| Schedule Agent | Находит конфликты, предлагает тайминг и уведомления | Не меняет опубликованное расписание без approval |
| Heat Builder Agent | Предлагает heats и порядок по заданным правилам | Human approval обязателен |
| Scoring Assistant | Проверяет арифметику, пропуски и аномалии | Не выставляет оценку и не публикует результат |
| Communications Agent | Готовит черновики сообщений и сегменты | Массовая отправка только после approval |
| Media Match Agent | Предлагает связь файла с Athlete ID по времени и метаданным | Спорные связи проверяет media operator |
| Incident Triage Agent | Сводит технические ошибки и предлагает escalation | Не скрывает инциденты и не закрывает критические кейсы |
| Archive Agent | Проверяет полноту архива и готовит manifest | Не переводит событие в archive без разрешения |
| QA Agent | Генерирует тестовые сценарии и проверяет acceptance criteria | Не подменяет реальные проверки среды |

Каждый agent работает только с allowlisted tools, пишет структурированный результат и создает audit event. Критические действия требуют явного подтверждения человека с подходящей ролью.

## 17. Обязательные исключения

| Проблема | Решение |
|---|---|
| Дубликат Athlete ID | Заблокировать commit, предложить merge review, не удалять историю автоматически |
| Один телефон у нескольких членов семьи | Поддержать связанные профили и явный выбор, не смешивать данные |
| Просроченная справка | Блокировать допуск до approved или manual override с причиной |
| Оплата списана, статус pending | Создать reconciliation case, не требовать повторную оплату автоматически |
| Участник поменял категорию | Новая версия заявки и повторная проверка места/платежа |
| Участник не пришел | DNS с временем и автором отметки |
| Участник прекратил выступление | DNF с причиной по правилам |
| Технический сбой scoring | Локальное сохранение, idempotent retry, ручная сверка |
| Нет сети | Offline queue, видимый last sync, запрет скрытого конфликта |
| Ошибка в протоколе | Correction workflow, новая версия, уведомление |
| Перенос из-за погоды | Версия расписания, затронутые heats и массовое подтверждение |
| Некорректная медиа-привязка | Снять публикацию файла, review, уведомить участника |
| Апелляция | Отдельный case, дедлайн, evidence, решение уполномоченного лица |
| Несовершеннолетний | Родительское согласие и отдельный access scope |
| Отзыв согласия на медиа | Убрать публичную выдачу, сохранить спортивный архив по правилам хранения |

## 18. Definition of Done для организатора

Сценарий готов, когда на тестовом и затем на реальном событии организатор может:

- создать событие и заполнить паспорт;
- загрузить и версионировать бюллетень, правила и документы;
- настроить категории, лимиты, платежи и дедлайны;
- открыть регистрацию по deep link;
- увидеть и проверить заявки;
- безопасно импортировать исходные таблицы в preview;
- выявить дубли и конфликты;
- проверить документы и оплаты;
- сформировать и зафиксировать roster;
- назначить судей и операционную команду;
- создать и опубликовать расписание;
- сформировать, проверить и опубликовать heats/start lists;
- принять check-in онлайн и через offline queue;
- управлять called/ready/on-water/completed/DNS/DNF/DSQ;
- ввести, проверить и lock оценки;
- опубликовать квалификацию, LCQ, полуфинал и финал;
- сформировать официальный протокол;
- обработать апелляцию и correction;
- настроить и отправить уведомления;
- принять и подтвердить фото/видео;
- перевести событие в completed и read-only archive;
- получить отчет по инцидентам, feedback и delivery;
- пройти негативные permission tests;
- восстановиться после повторной отправки, reconnect и конфликта;
- провести событие без Excel как основного Source of Truth.

## 20. Следующий конкретный шаг команды

После восстановления доступа к репозиторию команда должна реализовать один вертикальный organizer slice:

`создать тестовое событие → открыть регистрацию → проверить две заявки → собрать roster → назначить один heat → выполнить check-in → ввести score → утвердить result → сформировать protocol → archive`.

Для этого slice необходимо:

1. найти существующие модели и endpoints;
2. зафиксировать state machine и permissions;
3. добавить schema validation и idempotency;
4. написать unit/integration/permission tests;
5. проверить мобильный участник и desktop organizer;
6. обновить PRD, DATA_MODEL, API_CONTRACT, SECURITY, TESTING, RUNBOOK и CURRENT_STATE;
7. зафиксировать ограничения среды отдельным Validation Report.

Главный критерий организатора: система должна показывать не только «таблицу участников», а полный управляемый жизненный цикл соревнования — с ответственными, версиями, уведомлениями, официальным результатом и архивом.
