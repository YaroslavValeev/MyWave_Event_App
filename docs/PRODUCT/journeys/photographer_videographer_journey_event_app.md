# MyWave Event App — сквозной сценарий фотографа и видеографа

**Статус:** целевая спецификация для реализации и проверки  
**Дата:** 14.09.2026  
**Реализация 2026-09-17:** срез 1 в коде — сущность FieldMoment и вкладка «Моменты» (камера PWA). Полный контур ниже (EXIF, Athlete ID match, личный альбом) **ещё не сделан**.  
**Роли:** photographer, videographer, media manager  
**Продукт:** MyWave Event App; «Champ App» — рабочее название  

## 1. Назначение документа

Документ описывает полный медиаконтур соревнования: от назначения команды и подготовки медиаплана до выдачи спортсменам персональных фото/видео и закрытия архива.

В нем разделены:

- **Факты** — подтверждено материалами проекта, протоколами и требованиями к Athlete ID.
- **Целевой сценарий** — как должна работать media mode в приложении.
- **Критерии приемки** — что проверить на реальном событии.

Текущий доступ к GitHub-репозиторию `YaroslavValeev/MyWave_Event_App` возвращает 404, поэтому документ не утверждает наличие перечисленных функций в текущем коде.

## 2. Зачем Event App нужен медиаконтур

После соревнования спортсмен не должен искать себя вручную в общем архиве из тысяч файлов. Его профиль и событие должны автоматически показывать:

- только его фотографии;
- видео конкретных проездов;
- раунд и heat;
- дату и время съемки;
- автора материала;
- статус публикации;
- разрешение на скачивание и sharing.

Основная связка:

`Event ID + Athlete ID + round ID + heat ID + фактическое время выхода + media asset`.

Фактическое время выхода на воду важнее одного планового времени: расписание может сдвинуться, а медиа-сопоставление должно учитывать реальное событие.

## 3. Роли медиакоманды

| Роль | Ответственность | Ограничения |
|---|---|---|
| Media manager | Настраивает медиаплан, права, папки, workflow и публикацию | Не должен менять спортивные результаты |
| Photographer | Снимает фото, загружает и подтверждает фото-материалы | Не получает доступ к медицинским и финансовым данным |
| Videographer | Снимает проезды, ведет timecode и загружает исходники/превью | Не публикует спорно сопоставленное видео без проверки |
| Media editor | Отбирает, обрабатывает и готовит версии файлов | Не удаляет оригинал без политики хранения |
| Media reviewer | Проверяет качество и связь asset с Athlete ID | Спорное сопоставление подтверждает человек |
| Event manager | Утверждает публичность, сроки и общие материалы | Не меняет авторство и оригинальный файл без audit |
| Athlete | Видит свои подтвержденные материалы и сообщает об ошибках | Не видит чужие приватные assets |
| AI media agent | Читает метаданные, предлагает теги и совпадения | Не публикует и не удаляет спорные материалы самостоятельно |

## 4. Права и согласия

До начала съемки система должна хранить media consent участника:

- разрешено ли снимать;
- разрешена ли публикация имени;
- разрешена ли публикация фото;
- разрешена ли публикация видео;
- разрешено ли использование в трансляции;
- разрешен ли download оригинала;
- разрешено ли использование в промо/соцсетях;
- отдельное согласие родителя для несовершеннолетнего;
- срок действия и версия текста consent.

Публичность определяется не только наличием файла, но и действующим consent. Отзыв согласия запускает policy workflow: ограничение публичной выдачи, проверка уже опубликованных ссылок и фиксация решения в audit log.

Медицинские справки, страховые полисы, телефоны и внутренние документы не относятся к media mode и не должны попадать в альбомы, public links или AI prompts.

## 5. Состояния media asset

Каждый файл должен иметь отдельное состояние:

`received → validating → uploaded → metadata_extracted → suggested_match → review → approved → published → archived`.

Исключения:

- `rejected` — формат, размер, качество, нарушение прав;
- `needs_manual_match` — неуверенное сопоставление;
- `unpublished` — снят с публикации;
- `reported` — участник сообщил об ошибке;
- `quarantined` — подозрительный или поврежденный файл;
- `deleted_by_policy` — удален согласно сроку хранения.

Файл не должен отображаться спортсмену как его материал до перехода в `approved` или в явно обозначенный preview-режим.

- список фотографов и видеографов;
- роли и зоны доступа;
- категории и heats;
- точки съемки;
- плановые окна;
- необходимое оборудование;
- схема именования файлов;

- правила публикации;
- дедлайн выдачи материалов;
- контакт технической поддержки.

Каждый сотрудник получает приглашение с Event ID, ролью, сроком и инструкцией по загрузке.

### D‑21…D‑14: согласование Athlete ID и roster

Media manager получает не полный профиль спортсмена, а минимальный production roster:

- Athlete ID;
- публичное имя;
- стартовый номер;
- категория;
- регион/страна, если разрешено;
- раунд и heat;
- плановое время;
- статус consent.

Система должна позволять скачать офлайн-версию roster на устройство фотографа/видеографа. При изменении стартового листа создается новая версия и уведомление.

### D‑14…D‑7: медиаплан по раундам

Для каждого блока задаются:

- qualification;
- LCQ;
- semifinal;
- final;
- training;
- award ceremony;
- backstage/interview;
- general venue;
- partner integrations;
- broadcast inserts.

Media manager определяет минимальный обязательный результат:

- минимум один подтвержденный фото-пакет на участника;
- видео каждого доступного проезда, если съемка предусмотрена;
- hero shots финала;
- материалы для официального протокола/публикации;
- резервные общие кадры.

### D‑7…D‑1: dry run

Команда проверяет:

- login и role scope;
- QR/Athlete ID roster;
- синхронизацию стартовых листов;
- часы устройств;
- timezone;
- naming template;
- upload на тестовое событие;
- EXIF и timecode;
- слабую сеть;
- повторную загрузку;
- резервное устройство;
- доступ к preview;
- отмену ошибочного match;
- отсутствие утечки private data.

Часы камер и операторских устройств синхронизируются с официальным временем события. Расхождение времени должно фиксироваться в metadata, а не исправляться вручную без журнала.

## 7. Сценарий фотографа в день события

### 7.1. Открытие media mode

Фотограф входит в событие и видит:

- сегодняшний план;
- текущий блок;
- ближайший heat;
- список спортсменов;
- Athlete ID и стартовые номера;
- consent flags;
- точки съемки;
- состояние upload;
- свободное место;
- last sync.

В режиме площадки интерфейс должен работать на мобильном устройстве, но иметь крупные touch targets и быстрый поиск.

### 7.2. Перед heat

Фотограф открывает heat card:

- категория;
- раунд;
- номер heat;
- порядок участников;
- имя/публичное имя;
- Athlete ID;
- стартовый номер;
- плановое время;
- статус готовности;
- фактическое время выхода после фиксации координатором.

Можно заранее пометить приоритетные кадры, но нельзя скрыть остальных участников из обязательного покрытия без явного решения media manager.

### 7.3. Во время съемки

Фотограф снимает и сохраняет исходные файлы с EXIF. Если камера поддерживает передачу, приложение может принимать low-resolution preview, но оригинал сохраняется в утвержденном storage.

Система не должна требовать от фотографа вручную вводить ФИО для каждого кадра. Быстрый способ идентификации:

1. открыть текущий heat;
2. выбрать спортсмена или стартовый номер;
3. при необходимости отметить серию кадров;
4. продолжить съемку.

Если фактический порядок изменился, фотограф выбирает актуальный участник из live heat, а не из устаревшего списка.

### 7.4. После heat

Фотограф:

- выбирает лучшие кадры;
- загружает preview или оригиналы по политике события;
- проверяет предложенные Athlete ID;
- подтверждает очевидные совпадения;
- отправляет спорные кадры в `needs_manual_match`;
- добавляет теги раунда, heat и точки съемки;
- видит очередь `pending upload`;
- проверяет, что локальные файлы не потеряны.

Статус `uploaded` не означает `published`.

## 8. Сценарий видеографа

### 8.1. План записи

Videographer работает с таблицей:

- event ID;
- round;
- heat;
- Athlete ID;
- порядок;
- имя/публичное имя;
- плановое время;
- фактическое время выхода;
- camera ID;
- record start/end;
- timecode;
- status.

Если у события несколько камер, каждая получает собственный camera ID и правила синхронизации.

### 8.2. Фиксация проезда

Перед стартом оператор выбирает текущий heat и отмечает `recording`. После выхода на воду система фиксирует фактическое время, если оно пришло от координатора или scoring dashboard.

Минимальная единица видео — один проезд или один явно размеченный сегмент. Если записан длинный continuous file, приложение поддерживает chapters/clips:

- начало проезда;
- конец проезда;
- участник;
- раунд;
- heat;
- статус сопоставления.

### 8.3. Загрузка

Видеограф может сначала передать:

- thumbnail;
- proxy/preview;
- metadata;
- оригинал позже.

Участнику не отправляется тяжелый файл до готовности оптимизированной версии. Upload поддерживает resume после обрыва и idempotency key.

### 8.4. Сопоставление по времени

Система использует:

- фактическое время выхода;
- EXIF capture time;
- video timecode;
- camera clock offset;
- heat/порядок;
- длительность проезда;
- ручную отметку оператора.

AI media agent предлагает match с confidence score. Пример статусов:

- `high confidence` — можно отправить на быструю проверку;
- `medium confidence` — обязательный media review;
- `low confidence` — ручное сопоставление;
- `no match` — файл остается в общем media queue.

Ни один confidence score не заменяет согласие и human review спорного материала.

## 9. Media review

Reviewer видит карточку asset:

- preview;
- тип файла;
- автор;
- camera ID;
- EXIF/timecode;
- предложенный Athlete ID;
- confidence;
- heat/round;
- consent status;
- права использования;
- предыдущие решения;
- комментарий.

Действия:

- `Подтвердить связь`;
- `Выбрать другого спортсмена`;
- `Оставить общим событийному альбому`;
- `Отправить на ручную проверку`;
- `Снять с публикации`;
- `Карантин`;
- `Пожаловаться на качество`.

Если один asset связан с несколькими спортсменами, это должно быть явно обозначено. Нельзя скрывать групповое фото как персональное без корректной модели связей.

## 10. Выдача материалов спортсмену

После approval участник получает push:

- «Готовы фото с квалификации»;
- «Доступно видео вашего проезда LCQ»;
- «Добавлены материалы финала»;
- «В альбоме найдено новое фото».

Экран «Мои материалы» фильтруется по:

- событию;
- раунду;
- heat;
- дате;
- фото/видео;
- опубликовано/обрабатывается.

Для каждого asset отображается:

- preview;
- round/heat;
- время;
- автор;
- качество/размер;
- download/share;
- report mismatch.

Ссылка на оригинал имеет ограниченный срок, если это требуется политикой хранения. Скачивание и sharing журналируются, если материал коммерческий или ограниченный.

## 11. Общий альбом события и персональный альбом

Нужны два разных представления:

### Персональный альбом

Только подтвержденные связи с Athlete ID, доступные по consent.

### Общий альбом события

Общие кадры площадки, награждения, судей, партнеров и атмосферы. В него могут попадать материалы без конкретной привязки.

Поиск по общему альбому не должен быть обязательным путем к персональным материалам.

## 12. Материалы для трансляции и комментатора

Media manager может создать broadcast package:

- hero photo;
- athlete portrait;
- verified short clip;
- lower-third asset;
- public name;
- Athlete ID;
- category;
- round;
- result status;
- rights/consent.

Комментатор получает только approved public assets. Черновики, спорные файлы, приватные документы и внутренние комментарии недоступны.

AI может предложить короткий список кадров для паузы в эфире, но редактор утверждает финальную подборку.

## 13. Ошибки и исключения

| Ситуация | Поведение |
|---|---|
| Нет сети | Локальная очередь, last sync, запрет потери меток |
| Upload прерван | Resume, progress, повтор без дубля |
| Неверный Athlete ID | Снять публикацию, исправить связь, уведомить участника |
| Несинхронные часы камеры | Сохранить clock offset и отправить на manual review |
| Один файл подходит нескольким участникам | Групповая связь, не создавать ложное одиночное сопоставление |
| Нет уверенного match | Общий queue до ручной проверки |
| Просроченный consent | Заблокировать public publish |
| Участник пожаловался | `reported`, временно скрыть спорный asset |
| Плохое качество | Отправить на re-edit/reject, не выдавать как финал |
| Недостаток storage | Предупреждение media manager, приоритет originals и approved previews |
| Дубли файла | Content hash и idempotent ingest |
| Поврежденный файл | Quarantine и повторная загрузка |
| Изменился heat | Пересчитать match по версии start list |
| Событие перенесено | Не менять исходный capture time; связать с новой версией события |
| Удаление | Retention workflow, причина, audit |

## 14. Безопасность

- Проверять MIME, расширение, размер и content hash.
- Сканировать загружаемые файлы до публикации.
- Разделять оригиналы, preview и public derivatives.
- Использовать signed URLs с ограниченным сроком.
- Проверять роль на API для каждого media endpoint.
- Не включать PII в публичные имена файлов и ссылки.
- Не логировать полные URL с секретными query-параметрами.
- Учитывать consent до каждого уровня выдачи.
- Сохранять автора и историю изменений.
- Не удалять оригинал только из-за жалобы до принятия решения по policy.

## 15. Аналитика

Собирать без PII:

- время от capture до upload;
- upload success/failure;
- average processing time;
- media match rate;
- manual review rate;
- mismatch reports;
- время от approval до athlete notification;
- preview open rate;
- download rate;
- процент покрытых участников;
- процент покрытых раундов;
- доля материалов с consent;
- storage usage;
- duplicate/retry rate;
- offline conflict rate.

## 16. AI Agents и subagents

| Agent | Разрешенная работа | Запрещено |
|---|---|---|
| Ingest Agent | Читает metadata, считает hash, проверяет формат и размер | Публиковать файл |
| Tagging Agent | Предлагает раунд, heat, камеру, тип кадра | Переопределять подтвержденный tag |
| Timecode Match Agent | Сопоставляет capture/timecode с фактическим выходом | Считать match окончательным при низкой уверенности |
| Duplicate Agent | Ищет повторные assets | Удалять оригиналы автоматически |
| Rights Agent | Проверяет consent и public scope | Выдавать юридическое решение вместо owner policy |
| Quality Agent | Подсвечивает поврежденные, темные, пустые или неподходящие файлы | Оценивать спортивный результат |
| Delivery Agent | Готовит уведомления и персональные подборки | Отправлять спорные материалы |
| Broadcast Agent | Собирает approved package для эфира | Публиковать без editor approval |
| Archive Agent | Проверяет полноту и создает manifest | Переводить событие в archive без разрешения |

Каждый AI-вызов имеет версию, actor, structured output и audit event. Модель не получает медицинские документы, телефоны и лишние персональные данные.

## 17. Definition of Done

Медиаконтур готов, когда:

- media manager назначает команду и зоны;
- фотограф и видеограф входят только в разрешенное событие;
- roster содержит Athlete ID, heat и consent status;
- устройство может работать при временной потере сети;
- фото и видео проходят MIME/size/hash validation;
- исходники и preview разделены;
- EXIF/timecode сохраняются;
- фактическое время выхода доступно для сопоставления;
- AI предлагает match, но спорные связи подтверждает человек;
- участник видит только approved personal media;
- общий и персональный альбомы разделены;
- поддерживаются qualification, LCQ, semifinal и final;
- есть report mismatch и снятие с публикации;
- sharing/download защищены;
- материалы для трансляции включают права и consent;
- дубль upload не создает две записи;
- ошибка сети не приводит к потере файла или метки;
- все действия журналируются;
- после `completed` медиаматериалы входят в read-only archive;
- media package доступен без ручного поиска по общему архиву.

## 19. Следующий технический slice

Реализовать и проверить один поток:

`создать test event → создать 1 heat с 3 athletes → media operator получает roster → загрузить фото и длинное видео → сохранить EXIF/timecode → отметить фактическое время выхода → предложить match → подтвердить reviewer → выдать персональный preview athlete → отправить mismatch → снять и исправить связь → архивировать`.

Проверить отдельно:

- пропавшую сеть;
