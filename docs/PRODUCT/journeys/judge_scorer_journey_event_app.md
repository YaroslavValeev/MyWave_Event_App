# MyWave Event App — сквозной сценарий судьи и скорера

**Статус:** целевая спецификация для реализации и проверки  
**Дата:** 14.09.2026  
**Роли:** judge, chief judge, scorer, homologator  
**Продукт:** MyWave Event App; «Champ App» — рабочее название  

## 1. Назначение

Документ описывает работу судейской и скоринговой команды от получения назначения до подписания официального протокола и закрытия архива.

В нем разделены:

- **Факты** — подтверждено материалами проекта и предоставленными протоколами.
- **Целевой процесс** — что должно появиться в рабочем интерфейсе judge/scorer.
- **Критерии приемки** — что проверить до допуска к реальному соревнованию.

GitHub-репозиторий `YaroslavValeev/MyWave_Event_App` в подключенном доступе по-прежнему возвращает 404. Поэтому этот файл является спецификацией, а не утверждением, что все перечисленные функции уже есть в коде.

## 2. Факты и спортивный контекст

Согласованная архитектура MyWave Event App использует БД приложения как Source of Truth, а не Excel, сайт или чат. В Stage 1 уже предусмотрены роли, events, applications, roster, officials, documents, notifications и audit log; полноценные heats, scoring, публикация результатов и архив были определены как ключевой недостающий срез.

В предоставленных материалах встречаются реальные протоколы и стартовые листы wakeboard boat:

- квалификация и LCQ;
- финальные стартовые листы;
- категории Open Men, Open Women, Junior Men, Over 30 Master Men;
- поля Name, Country, Categ., Score;
- квалификационный результат с общим Score и компонентами Execution, Intensity, Composition;
- отметка `Q` для прошедших дальше;
- реквизиты Chief Judge, Homologator и Scorer.

Это означает, что система должна поддерживать не одну универсальную формулу, а конфигурируемые scoring schemas для конкретного регламента, дисциплины, категории и версии правил. Числовые коэффициенты, количество заездов и критерии не должны быть жестко зашиты в интерфейс.

## 3. Роли и границы полномочий

| Роль | Основная задача | Критические права |
|---|---|---|
| Judge | Оценивает конкретный run по опубликованным критериям | Вводит и отправляет свои оценки; не видит и не меняет оценки других судей до разрешенного момента |
| Chief Judge | Руководит судейством и утверждает итог раунда | Проверяет отклонения, подтверждает lock, разрешает предусмотренные исправления и апелляции |
| Scorer | Ведет score sheet и расчет | Вводит/проверяет данные, запускает расчет, готовит draft result; не утверждает собственное официальное решение в одиночку |
| Homologator | Подтверждает соответствие условий, категории и регламентных параметров | Фиксирует технический статус и замечания; не редактирует оценки судьи без процедуры |
| Event manager | Управляет расписанием, heats и коммуникацией | Не меняет оценки и не публикует официальный результат вместо chief judge |
| Technical operator | Поддерживает устройства, сеть, синхронизацию и трансляцию | Не получает право изменять спортивные данные без отдельной роли |
| Athlete | Видит только опубликованный и разрешенный результат | Не может видеть черновики и внутренние судейские комментарии |

### Maker-checker

Критический путь обязан разделять:

`ввод оценки → расчет → проверка → утверждение → публикация → архив`.

AI не заменяет судью, chief judge, homologator или официальную комиссию. Он может найти пропуск, арифметическую аномалию, конфликт версии и подготовить сообщение, но не может выставить оценку, изменить Q/DNS/DNF/DSQ, принять апелляцию или опубликовать официальный результат без human approval.

## 4. Состояния scoring-процесса

### 4.1. Состояние соревнования

`configured → roster_locked → schedule_published → live → results_pending → results_verified → published → completed → archived`.

### 4.2. Состояние heat

`scheduled → called → ready → on_water → scoring → review → locked → published`.

### 4.3. Состояние run

`not_started → on_water → completed → score_draft → submitted → calculation_ready → verified → official → appealed / corrected`.

### 4.4. Статусы участника

`checked_in`, `ready`, `completed`, `DNS`, `DNF`, `DSQ`, `withdrawn`.

Статус `DNS`, `DNF` или `DSQ` требует причины, автора и времени. Нельзя заменить отсутствующий балл нулем без явного спортивного правила.

## 5. Временная шкала

### D‑30…D‑14: назначение и доступ

Chief judge или event manager назначает судейскую команду и отправляет приглашение.

Приглашение содержит:

- событие, даты и место;
- дисциплины и категории;
- роль;
- ожидаемые смены;
- ссылку на правила и бюллетень;
- требования к устройству и сети;
- срок подтверждения;
- контакт chief judge и технической поддержки.

После входа по телефону/OTP пользователь видит только события, к которым у него есть доступ. Для судьи должны быть скрыты финансовые данные, медицинские документы и приватные поля участников, не нужные для scoring.

### D‑14…D‑7: настройка scoring schema

Chief judge совместно со scorer выбирает или создает версию схемы:

- дисциплина;
- категория;
- раунд;
- число проездов;
- критерии;
- допустимый диапазон значений;
- шаг значения;
- правила округления;
- веса;
- минимальный набор обязательных полей;
- критерии tie-break;
- порядок применения штрафов;
- допустимые статусы DNS/DNF/DSQ;
- правила прохода в следующий раунд;
- версия регламента;
- дата публикации схемы.

Для wakesurf или другой дисциплины поля могут отличаться от wakeboard boat. В качестве примера из предоставленных материалов встречаются Execution, Intensity и Composition, однако приложение не должно считать этот набор универсальным для всех соревнований.

До открытия live-сессии система показывает preview:

- как вводит judge;
- как видит scorer;
- как выглядит результат у участника;
- пример расчета на synthetic fixture;
- все округления и tie-break;
- журнал версии.

Изменение scoring schema после первого run блокируется. Если регламент требует изменения, создается новая версия с причиной и approval chief judge.

### D‑7…D‑1: dry run

Скоринговая команда прогоняет не менее следующих тестов:

- обычный полный run;
- неполное заполнение;
- минимальные и максимальные значения;
- одинаковые баллы и tie-break;
- DNS;
- DNF;
- DSQ;
- один судья не отправил оценку;
- повторное нажатие Send;
- потеря сети;
- восстановление сети;
- смена устройства;
- изменение heat до начала;
- отмена run из-за погоды;
- correction до lock;
- correction после publication.

Результаты dry run помечаются synthetic и не смешиваются с production event.

## 6. Рабочее место судьи

Judge может работать на планшете или ноутбуке; интерфейс должен быть пригоден для быстрого ввода на площадке.

### 6.1. Экран «Мои события»

Показывает:

- событие;
- дата и место;
- назначенная роль;
- ближайшая смена;
- количество heats;
- состояние подключения;
- кнопку «Открыть судейскую панель».

### 6.2. Экран «Текущий heat»

Содержит:

- категорию и раунд;
- номер heat;
- текущего спортсмена;
- порядковый номер;
- публичное имя и Athlete ID;
- страну/регион, если это разрешено;
- плановое и фактическое время выхода;
- status bar;
- таймер;
- предыдущие результаты только в разрешенном объеме;
- кнопку `DNS`, `DNF`, `DSQ` с обязательной причиной;
- кнопку перехода к форме оценки.

Нельзя показывать судье неподтвержденные приватные сведения участника. В режиме соревнования крупные touch targets и минимум второстепенной информации важнее плотности таблицы.

### 6.3. Форма оценки

Форма строится из активной scoring schema. Для каждого критерия:

- название и короткое пояснение;
- диапазон;
- единица/шаг;
- поле значения;
- необязательный комментарий;
- подсветка ошибки;
- возможность исправить до отправки.

Внизу:

- предварительный subtotal, если он разрешен;
- индикатор заполненности;
- предупреждения;
- кнопка `Сохранить черновик`;
- кнопка `Отправить оценку`.

Кнопка отправки становится доступной только при заполнении обязательных полей и валидных значениях. После submit судья видит `Отправлено в scoring queue`, но не может бесследно перезаписать запись.

### 6.4. Повторный ввод и исправление

Если судья обнаружил ошибку до lock:

1. открывает свой run;
2. выбирает `Запросить исправление`;
3. указывает причину;
4. система создает новую версию;
5. scorer и chief judge получают уведомление;
6. только разрешенный пользователь подтверждает correction.

После публикации судья не редактирует официальный результат напрямую.

## 7. Рабочее место скорера

### 7.1. Scoreboard

Scorer видит:

- список текущих и следующих heats;
- статус каждого run;
- сколько судей отправили оценку;
- пропуски;
- вычисленный subtotal/total;
- warnings;
- Q/не прошел;
- время последнего обновления;
- sync status.

Цвет не должен быть единственным индикатором. Каждый статус сопровождается текстом и иконкой.

### 7.2. Карточка run

Карточка содержит исходные данные:

- event ID;
- round ID;
- heat ID;
- Athlete ID;
- публичное имя;
- стартовый номер;
- фактическое время выхода;
- judge entries;
- schema version;
- calculation version;
- статусы DNS/DNF/DSQ;
- история изменений;
- media reference, если используется.

Scorer не должен вручную копировать имя из Excel или протокола: участник выбирается по Athlete ID и roster.

### 7.3. Проверки до расчета

Система автоматически проверяет:

- все обязательные оценки получены;
- значения лежат в диапазоне;
- не использована неверная schema version;
- run относится к правильному heat;
- участник допущен и checked-in;
- нет дубля submit;
- время выхода возможно;
- DNS/DNF/DSQ не конфликтует с score;
- нет незакрытого correction case;
- все судьи имеют нужную роль.

Scorer получает очередь `needs attention` с конкретным описанием проблемы.

### 7.4. Расчет

Расчетный движок должен быть детерминированным и версионированным. Для каждого результата сохраняются:

- исходные оценки;
- примененная scoring schema;
- версия calculation engine;
- промежуточные значения;
- округления;
- штрафы;
- tie-break;
- итог;
- время расчета.

Приложение не должно показывать только одно итоговое число, если регламент предусматривает компоненты. В UI участника отображаются только те компоненты, которые разрешены правилами публикации.

## 8. Chief judge review

Chief judge получает список `results pending review`.

Для каждой строки видит:

- категорию, раунд, heat;
- участника и Athlete ID;
- оценки по судьям в разрешенном формате;
- итог;
- отклонения и warnings;
- DNS/DNF/DSQ;
- комментарии;
- историю correction;
- связанный incident.

Действия:

- `Подтвердить результат`;
- `Вернуть scorer на исправление`;
- `Запросить пояснение`;
- `Отметить technical issue`;
- `Зафиксировать ручное решение` — только с причиной и ссылкой на регламент;
- `Открыть апелляцию`;
- `Lock round`.

После lock изменения обычными кнопками невозможны. Ручное решение не скрывает исходные значения и не удаляет audit trail.

### 8.1. Что считать аномалией

Система может подсветить для проверки:

- отсутствующую оценку;
- выход за диапазон;
- резкое отличие от других judge entries;
- невозможную комбинацию статусов;
- повторный submit;
- неправильную категорию;
- результат без check-in;
- расхождение с предыдущей версией;
- нарушенный порядок прохода.

Аномалия — это повод проверить, а не автоматическое доказательство ошибки.

## 9. Homologator и техническая проверка

Homologator фиксирует параметры, которые влияют на валидность результата:

- соответствие дисциплине и категории;
- пригодность воды/площадки;
- фактический формат heat;
- технические ограничения;
- interruptions;
- погодные или safety conditions;
- разрешение продолжать или остановить блок.

Если условия влияют на результат, homologator создает record с типом, временем, доказательством и решением chief judge. Нельзя менять score задним числом без ссылки на такой record и новую версию результата.

## 10. Работа по раундам

### Квалификация

Scorer открывает раунд, проверяет roster и порядок, принимает оценки и готовит draft standings. После lock система применяет правила прохода.

### LCQ

LCQ имеет собственный heat и собственную scoring session. Нельзя автоматически смешать его с qualification score, если регламент этого не предусматривает. В интерфейсе участника показывается отдельная карточка LCQ и отметка `Q`, если спортсмен прошел дальше.

### Полуфинал

Список участников формируется только из verified results предыдущего раунда. Ручное добавление требует причины и approval chief judge.

### Финал

Перед финалом chief judge подтверждает roster и scoring schema. После финала обязательно выполняются result verification, official protocol generation и publish.

## 11. Публикация результатов

Публикация — отдельная операция, не равная расчету.

Перед publish система показывает:

- event;
- дисциплину и категорию;
- round;
- список мест;
- все статусы DNS/DNF/DSQ;
- tie-break;
- число verified runs;
- предупреждения;
- версию протокола;
- автора публикации;
- время.

Publish доступен только после:

- lock всех требуемых runs;
- chief judge approval;
- homologator status, если необходим;
- проверки отсутствия blocking warnings;
- подтверждения scorer;
- генерации protocol snapshot.

Участник получает уведомление «Официальный результат опубликован». До этого он видит только `draft` или `результат формируется`.

## 12. Протокол и интеграции

Официальный протокол должен иметь:

- стабильный event ID;
- версию;
- дату и часовой пояс;
- дисциплину и категорию;
- раунды;
- Athlete ID;
- публичное имя;
- порядковые номера;
- баллы и разрешенные компоненты;
- Q/DNS/DNF/DSQ;
- chief judge, homologator и scorer;
- подписи/подтверждения, если предусмотрены;
- checksum или иной способ доказать целостность.

Экспорт в PDF/CSV/JSON допустим как представление опубликованных данных, но не как отдельный источник истины. После публикации протокол может передаваться в ParserNews или другие системы только как verified result source и с указанием версии.

## 13. Апелляции и corrections

### Апелляция участника

Участник открывает официальный результат, видит срок апелляции и отправляет обращение с текстом/доказательствами. Судья не отвечает в обход системы так, чтобы решение не попало в журнал.

Статусы:

`submitted → acknowledged → under_review → decision_recorded → closed`.

### Исправление до публикации

Можно вернуть run на correction. Старая версия сохраняется, новая получает причину и авторов.

### Исправление после публикации

Только уполномоченный процесс:

1. зафиксировать issue;
2. указать affected results;
3. сохранить исходную версию;
4. сформировать corrected snapshot;
5. получить approvals;
6. опубликовать новую версию;
7. уведомить затронутых участников;
8. записать событие в audit.

## 14. Offline и отказоустойчивость

Судья и scorer должны видеть:

- `online`;
- `offline`;
- `syncing`;
- `sync conflict`;
- `error`;
- последнее время синхронизации.

В offline разрешается:

- открыть заранее загруженный heat;
- ввести оценку;
- сохранить локальный draft;
- повторить отправку после reconnect.

Нельзя разрешать:

- дважды применить одну оценку;
- тихо перезаписать более новую версию;
- публиковать официальный результат без серверного подтверждения;
- удалять локальную запись до успешной синхронизации.

Каждая операция имеет idempotency key. Конфликт показывает участнику команды обе версии и требует выбора уполномоченного человека.

## 15. Уведомления

Судейская команда получает:

- назначение и изменение роли;
- опубликованную scoring schema;
- напоминание о dry run;
- приближение смены;
- открытие heat;
- пропущенную оценку;
- blocking warning;
- возврат на исправление;
- запрос chief judge;
- lock раунда;
- публикацию протокола;
- correction/appeal;
- offline/sync conflict;
- incident escalation.

Массовые сообщения участникам публикуются только после human approval. Внутренние судейские комментарии не отправляются спортсмену автоматически.

## 16. AI Agents и subagents

| Agent | Что делает | Запрещено |
|---|---|---|
| Rules Agent | Извлекает структуру правил и подсвечивает несоответствия конфигурации | Самостоятельно утверждать правила |
| Schema Agent | Проверяет полноту scoring schema и генерирует preview | Менять схему после старта |
| Scoring QA Agent | Проверяет диапазоны, пропуски, арифметику и версии | Выставлять оценку |
| Heat/Status Agent | Следит за статусами heat и конфликтами порядка | Менять DNS/DNF/DSQ без человека |
| Anomaly Agent | Подсвечивает необычные расхождения | Объявлять ошибку доказанной |
| Protocol Agent | Собирает draft PDF/CSV/JSON и manifest | Публиковать без approval |
| Appeal Triage Agent | Классифицирует обращения и сроки | Принимать решение по апелляции |
| Sync Agent | Помогает разбирать очереди и конфликты | Тихо удалять или перезаписывать данные |
| Communication Agent | Готовит черновики уведомлений | Делать массовую отправку без approval |
| Audit Agent | Проверяет полноту журнала действий | Редактировать или скрывать audit |

Каждый вызов AI должен иметь allowlisted tool, structured output, версию prompt/правил, actor и audit event. Чувствительные данные участников не отправляются без необходимости.

## 17. Безопасность и приватность

- Судья видит только нужные спортивные данные.
- Медицинские справки, страховые полисы и телефон не попадают в judge UI без специальной необходимости.
- Athlete ID не содержит ФИО, телефон или дату рождения.
- Токены, OTP и платежные данные не попадают в логи.
- Все права проверяются на API, а не только в интерфейсе.
- Upload scoring attachments проверяет MIME, размер и права.
- Официальные ссылки на протоколы и медиа имеют ограниченный срок, если это требуется политикой.
- Экспорт официальных данных журналируется.
- Негативные permission tests обязательны для каждого endpoint.

## 18. Аналитика судейского процесса

Собирать без PII:

- время от вызова heat до complete scoring;
- долю своевременных submit;
- долю correction;
- количество пропущенных оценок;
- количество blocking warnings;
- среднее время chief judge review;
- время от последнего run до публикации;
- число апелляций;
- число и причины DNS/DNF/DSQ;
- долю offline операций;
- sync conflict rate;
- protocol generation/publish success rate;
- число corrections после публикации.

## 19. Definition of Done

Судейский контур готов, когда:

- chief judge создает/выбирает версию scoring schema;
- judge получает назначение и входит только в разрешенное событие;
- scorer видит правильный roster, heat и Athlete ID;
- judge вводит оценки по критериям с валидацией диапазонов;
- черновик сохраняется и повторная отправка не создает дубль;
- scorer видит полноту entries и blocking warnings;
- calculation engine детерминирован и версионирован;
- chief judge проверяет и блокирует раунд;
- homologator фиксирует технические условия;
- поддерживаются qualification, LCQ, semifinal и final;
- корректно обрабатываются DNS/DNF/DSQ;
- tie-break определяется опубликованным правилом;
- официальный результат нельзя опубликовать без необходимых approvals;
- участник не видит draft;
- correction после publish создает новую версию и уведомление;
- апелляция имеет срок и статус;
- offline queue и reconnect не создают дублей;
- audit log содержит все критические действия;
- protocol PDF/JSON/CSV строится из БД;
- событие можно завершить и перевести в read-only archive;
- тестовый прогон проходит без Excel как Source of Truth.

## 21. Следующий технический slice

Команде следует начать с одного полностью проверяемого потока:

`создать Open Men → добавить 5 athletes → назначить 3 judges и scorer → создать qualification heat → ввести оценки → рассчитать → проверить chief judge → отметить Q → опубликовать qualification result → сформировать LCQ → завершить архив`.

После этого прогнать тот же поток для финала и проверить:

- отсутствие дублей при двойном tap;
- DNS/DNF;
- неверный диапазон;
- offline submit;
- correction до lock;
- correction после publish;
- апелляцию;
- попытку доступа к чужому событию;
- неизменность опубликованного протокола.

Главный критерий: судья вводит только свою оценку, scorer управляет расчетом, chief judge принимает официальное решение, а приложение сохраняет каждую версию и делает результат понятным участнику.
