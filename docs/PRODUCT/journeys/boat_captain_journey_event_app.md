# MyWave Event App — сценарий капитана и водителя катера

**Дата:** 14.09.2026  
**Статус:** целевая спецификация для реализации и проверки  
**Роль:** captain / boat driver / driver operator

## 1. Назначение

Капитан или водитель катера отвечает за безопасный и своевременный выход участников на воду, соблюдение операционных cue и передачу фактического времени старта в Event App. Он не является судьей и не меняет результаты.

## 2. Данные, которые нужны капитану

Капитан видит минимум:

- событие и место;
- дату и часовой пояс;
- текущий раунд и heat;
- порядок участников;
- публичное имя;
- Athlete ID или стартовый номер;
- ready/called/on-water/completed;
- фактическое время выхода;
- safety/hold cue;
- контакт coordinator и chief judge;
- технические ограничения катера.

Капитану не показываются:

- медицинская справка;
- страховой полис;
- финансовые статусы;
- judge entries;
- draft scores;
- приватные контакты без необходимости.

## 3. Тайминг

### D‑30…D‑14

- подтверждение назначения;
- указание катера, экипажа и смен;
- загрузка safety plan;
- проверка лицензий и технических документов по правилам организатора;
- знакомство с форматом дисциплин и раундов;
- получение контактов chief judge и launch coordinator.

### D‑14…D‑7

- изучение стартовых листов;
- проверка схемы команд и сигналов;
- dry run статусов;
- проверка способа фиксации фактического времени;
- согласование emergency stop и weather hold.

### D‑1

- подтверждение катера и резервного оборудования;
- проверка fuel/battery/radio;
- синхронизация часов;
- загрузка offline heat pack;
- подтверждение первой смены.

## 4. День соревнований

### До открытия

Капитан проходит check-in, получает briefing и подтверждает:

- катер;
- экипаж;
- водителя;
- радиоканал;
- emergency signal;
- правила выхода;
- ближайший heat;
- резерв при задержке.

### Перед heat

1. Открывает последнюю версию heat.
2. Проверяет порядок и статус ready.
3. Подтверждает готовность катера.
4. Получает `called` от coordinator.
5. Принимает спортсмена по установленной процедуре.
6. Нажимает `on_water` только после фактического выхода.

### Во время

Капитан передает:

- начало выхода;
- фактическое время;
- hold;
- interruption;
- технический issue;
- завершение проезда.

Если приложение недоступно, используется локальная очередь; после восстановления связи captain или coordinator подтверждает фактическое время.

### После heat

- подтверждает completed;
- отмечает технические замечания;
- передает информацию scorer/coordinator;
- закрывает checklist.

## 5. Safety workflow

Статусы:

`normal → caution → hold → emergency_stop → cleared`.

Капитан может инициировать hold/emergency stop по safety procedure. Дальнейшее возобновление требует подтверждения authorized lead.

Инцидент содержит:

- event ID;
- heat;
- время;
- зона;
- тип сигнала;
- краткое описание;
- действия;
- ответственный;
- статус.

Нельзя указывать диагнозы и лишние персональные сведения в operational note.

## 6. Изменение расписания

При задержке:

1. координатор создает изменение;
2. event director/chief judge утверждает применимость;
3. капитан получает новую версию;
4. он подтверждает прием;
5. participant/heat marshal получают соответствующее уведомление.

Капитан не переставляет участников по личной договоренности.

## 7. Роли AI

AI может:

- показать следующий heat;
- напомнить о ready и hold;
- подсветить устаревшую версию списка;
- предложить сверку времени;
- свести технические notes.

AI не может:

- дать команду, противоречащую safety lead;
- изменить start list;
- присвоить DNS/DNF;
- изменить score;
- закрыть emergency case.

## 8. Definition of Done

- капитан видит только нужный heat;
- start list имеет версию;
- фактическое время фиксируется отдельно от планового;
- hold/emergency stop доступны быстро;
- offline queue не теряет событие;
- повторная отправка не создает дубль;
- captain не изменяет scoring;
- incident передается coordinator и safety lead;
- после события временный доступ отзывается;
- все действия попадают в audit log.

## 9. Первый технический slice

`назначить капитана → выдать heat → подтвердить ready → зафиксировать on_water → отметить interruption → завершить run → синхронизировать offline запись → передать handover coordinator`.

Главный критерий: в системе достоверно фиксируется, кто, в каком heat и когда фактически вышел на воду, без риска подменить спортивное решение.
