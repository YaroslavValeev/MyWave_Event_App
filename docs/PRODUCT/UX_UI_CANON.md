# Champ App UX/UI Canon 1.0

Статус: канонический  
Дата: 2026-09-15  
Итерация: **Role Based + Live First**  
Владелец: MyWave

Связанные документы: [PRD.md](./PRD.md), [USER_ROLES_AND_JOURNEYS.md](./USER_ROLES_AND_JOURNEYS.md), [AGENTS.md](../../AGENTS.md), [CURRENT_STATE.md](../STATUS/CURRENT_STATE.md).

---

## 1. Главное продуктовое правило

Пользователь с минимальными усилиями понимает:

1. где он находится;
2. что происходит на соревновании сейчас;
3. что относится лично к нему;
4. что требует его внимания;
5. что он должен сделать следующим;
6. что произойдёт после действия.

Интерфейс — **task-first**, не **module-first**.  
Показывать: что происходит сейчас → что важно этому пользователю → какое действие следующее.  
Не показывать в первую очередь перечень всех функций.

---

## 2. Russian-only UI

Весь production UI — **только русский**: навигация, меню, вкладки, заголовки, кнопки, формы, placeholder, статусы, роли, loading/empty/error, onboarding, уведомления, confirmation, a11y labels, экспорты для пользователя.

В production UI запрещены технические английские значения (`draft`, `verified`, `published`, `heat`, `participant`, `judge`, `token expired`, `API`, `debug`, `dev` и аналоги).

Внутри кода, API и БД английские identifiers сохраняются. Перед выводом — presentation mapping:

| API / код | UI |
|-----------|-----|
| `draft` | Черновик |
| `verified` | Проверен |
| `published` | Опубликован |
| `void` | Аннулирован |
| `heat` | Заезд |
| `participant` | Участник |
| `judge` | Судья |

Централизованно: `apps/web/src/lib/labels.ts`, `roles.ts`.  
Запрещено разрозненно переводить строки в компонентах разными формулировками для одного кода.

---

## 3. Не ломать фундамент

Сохраняем: API + БД как SoT; event-centric model; RBAC; Athlete ID; scoring; workflow результатов; audit; archive lock; checklist; documents; protocol capture; guest mode; session recovery; API contracts.

Меняем прежде всего: presentation, navigation, IA, компоненты, user flows.  
Backend не переписывать без объективной необходимости.

---

## 4. Проблема текущей IA

Карточка события не должна одновременно быть кабинетом всех ролей через 10 равных вкладок. Даже при role-based hiding плоская IA слишком тяжёлая для организатора.

---

## 5. Один продукт — разные role-based experience

Не отдельные приложения. Общие Design System и данные. Разное рабочее пространство:

| Режим | Русское имя |
|-------|-------------|
| Athlete Mode | Участник |
| Judge Mode | Судья |
| Organizer Control Room | Организатор |
| Broadcast / Commentator | Комментатор |
| Public Mode | Гость |

---

## 6. Athlete Mode

Главный вопрос: **Что происходит со мной на этом соревновании сейчас?**

Первый экран: **Мой старт** (категория, заезд, стартовый номер, время, очередь, статус: зарегистрирован → check-in → готов → следующий → на старте → завершил) + CTA «Открыть стартовый список».

Ниже: **Моя заявка**, **Допуск**, **Мой результат** (когда есть).  
**MyWave Athlete ID** — продуктовая сущность, не сырой текст профиля.

---

## 7. Athlete Card

Компонентная модель Digital Athlete Card: фото, ФИО, `MW-…`, город, дисциплины, статистика, QR/ID. Связи с профилем/историей/медиа — позже; сейчас заложить компонент.

---

## 8. Organizer Control Room

Операционный dashboard: название, город, день, статус **ИДЁТ СЕЙЧАС**; блоки **Сейчас / Следующий / Следующий заезд**; ключевой блок **Требует внимания** (недостающие оценки, check-in, заявки, публикация, протокол). Организатор не ищет проблемы по 10 разделам.

---

## 9. Judge Mode

Экран **Сейчас оценивается**: номер, ФИО, категория, заезд → критерии → итог → **Сохранить оценку** → следующий спортсмен. Минимизировать риск оценки не тому участнику (не длинный dropdown текущей цели).

---

## 9.1. Полевые моменты (камера)

Отдельная вкладка **Моменты**, не протокол судьи. Кто снимает: медиа, комментатор, поддержка/маршал, организатор, главный судья. Точка съёмки: бэкстейдж, глазами пилота, маршал на старте, на воде, зрители. На телефоне — системная камера (`<input capture>`). Кадры не на витрине гостя; «Для эфира» — решение организатора.

---

## 10. Live Heat / Start List

Один contextual primary action по статусу:

- Регистрация → **Готов**
- Готов → **На воде**
- На воде → **Финиш**

DNS / DNF / откат / ручное — в меню `•••`.

---

## 11. Результаты

Структура: место · спортсмен · балл · судьи · статус. CTA **Опубликовать результаты** только по business rules. Workflow: Черновик → Проверен → Опубликован → Аннулирован (русские лейблы).

---

## 12. Комментатор

Read-heavy: кто сейчас, кто следующий, стартовый список, live-status, профиль/регион/клуб, прошлые результаты, заметки. Архив/KB/broadcast — позже.

---

## 13. Public Mode

Без регистрации: публичные события, расписание, LIVE, опубликованные результаты, разрешённые публичные данные.

---

## 14. Экран «События»

Секции: **Идёт сейчас** · **Ближайшие** · **Мои соревнования** · **Архив**.  
«Ближайшее» — по `status` + `starts_at` / `ends_at`, не `items[0]`.

---

## 15. Главная

Смысл: «Заявка, старт и протокол — в одном месте».  
Подзаголовок ценности: всё соревнование в одном приложении (регистрация, расписание, стартовые списки, судейство, результаты в реальном времени).

Гость: primary **Найти соревнование**, secondary **Войти**, text **Создать аккаунт**.

---

## 16. Bottom Navigation

Мобильно 4–5 destinations. Не дублировать desktop механически.

- Участник: Главная · События · Уведомления · Профиль  
- Судья (на событии): Судейство · Заезды · Результаты · Ещё  
- Организатор: Control · Участники · Спорт · Ещё  

**Выйти** — не destination; только Профиль / Настройки.

---

## 17. Регистрация

Короткий сценарий: ФИО, телефон, email, **Создать аккаунт**.  
Согласия: необходимые vs дополнительные.

---

## 18. Event-role

Судья / комментатор / представитель команды — не ложная глобальная роль. Запрос роли в контексте события → решение организатора.

---

## 19. Вход и OTP

Пароля нет. Роль не выбирается на форме входа — она уже привязана к номеру в аккаунте.

Пока SMTP не настроен (local/staging): форма только «Телефон» → «Войти». Когда SMTP или production — явно «Код подтверждения придёт на email, привязанный к аккаунту». После отправки — маска email, без угадывания канала.

---

## 20. Уведомления

Actionable + deep-link (P0/P1): открыть соревнование / стартовый список / судейство / результаты.

---

## 21. Ошибки

Без «Проверьте, что API запущен». Пример: «Не удалось загрузить соревнования» + **Повторить**. Техпричина — в logging.

---

## 22. Документы и CTA

Любой видимый CTA обязан иметь работающий action, feedback и error state. Не показывать «Удалить», если действие не работает.

---

## 23. Формы

Общие: Input, Select, NumberInput, SearchInput, FileUpload, Checkbox, Field, FieldError. Placeholder не заменяет label. Без хаотичных inline-styles на controls.

---

## 24. Design System 1.0

Spacing: **4 / 8 / 12 / 16 / 24 / 32 / 48**.  
Radius: controls **8**, cards **12**, panels **16**, badges **999**.  
Buttons: Primary, Secondary, Tertiary, Danger, Icon.  
States: default, hover, pressed, focus, disabled, loading, success, error.

---

## 25–27. Visual / цвет / WOW

Спортивный, точный, быстрый, профессиональный, живой, чистый, premium — через иерархию, типографику, состояния, restrained motion; не через декоративный шум.

Brand accent: MyWave turquoise — функционально, не на всём сразу. Semantic: Brand/Action, Neutral, Success, Warning, Danger, **LIVE** (отдельно от info).

Meaningful moments: заявка принята, «Вы следующий», результат опубликован, подиум + поделиться.

---

## 28. Accessibility

Touch ≥ 44×44; visible focus; labels; цвет не единственный индикатор; contrast; a11y loading/error; SR labels на русском; `tablist/tab/tabpanel`, `aria-labelledby/controls`, стрелки для tabs; text scaling.

---

2. Events: Идёт сейчас / Ближайшие / Мои / Архив.

5. Notifications actionable/deep-link.  
6. Починить неработающие CTA (в т.ч. документы).  
7. Светлые controls без тёмных inline-styles.  
8. Field/Input/Select.  
9. «Следующий шаг» на event home.  
10. Упростить status-actions в live heat.

1. Product/UX architecture (роли)  
2. Navigation  
3. Live Competition  
4. Design System 1.0

---

## 31. Правило для AI-агентов

Перед UI-изменениями читать: `AGENTS.md`, `CANONICAL_DOCS_INDEX.md`, `PRD.md`, `USER_ROLES_AND_JOURNEYS.md`, **этот файл**, `CURRENT_STATE.md`.  
Расхождение код↔канон — явно зафиксировать и исправить код или обновить док. Нельзя молча менять UX-модель.

---

## 32. Definition of Done (UI-задача)

Русские строки; нет английских технических статусов в UI; loading/empty/error; feedback успеха; mobile; focus/keyboard; a11y; учёт роли; понятен следующий шаг; нет дублирующего компонента; нет случайного inline-style вместо DS; канон обновлён при смене flow.

---

## 33. Анти-паттерны

Не: переписывать backend ради redesign; ломать working flows до замены; отдельные app per role; английский UI; animation вместо feedback; гигантский PR со всем redesign.

Приоритет: сделать существующую функциональность профессионально используемой на реальном соревновании. Benchmark: организатор, спортсмен и судья без обучения интерфейсу.

**Канон проверки новых UX/UI:** Role Based + Live First + Russian-only UI.
